# keykeep_psono — Personal Password Vault (psono-protocol)

Zero-knowledge personal password vault embedded in Odoo as HTTP controllers,
byte-compatible with the psono protocol (verified against psono-web v4.8.0 and
psono-server 7.3.6).

**Trust model:** client-side encryption. The server stores only ciphertext,
nonces and wrapped keys — Odoo administrators cannot read vault contents.
The user's master password never leaves the browser.

**Identity:** each vault user is tied 1:1 to a `res.users` record by email.
Registration is gated by the Odoo session (no open registration).

## Architecture

```
psono-web v4.8.0 (static, served from Odoo at /keykeep/psono/web/)
   │  config.json is GENERATED by Odoo (see "Client configuration" below)
   │  SERVER_URL = <host>/keykeep/psono
   ▼
Caddy (ledningssystem.vertel.se)
   ├── rate_limit on /keykeep/psono/authentication/{prelogin,login,register}*
   └── reverse_proxy → Odoo
        ▼
Odoo http.Controller  /keykeep/psono/*
   ├── /info/                 signed TOFU info (Ed25519)
   ├── /authentication/       prelogin, login (Box exchange), register,
   │                          verify-email, activate-token, logout
   ├── /user/status/          status polling
   ├── /datastore/            list (GET), create (PUT), update (POST), detail
   ├── /secret/               create (PUT), update (POST), read (GET <id>/)
   ├── /secret/history/<id>/  version history
   ├── /bulk-secret/          bulk create (used by import)
   ├── /recoverycode/         register/replace recovery material (POST)
   ├── /password/             recovery step 1 (POST) + step 2 (PUT)
   ├── /user/delete/          delete own vault (DELETE, disabled by default)
   ├── /share/right/          {"share_rights": []} (MVP)
   └── /avatar/               {"avatars": []} (MVP)

Models: keykeep.psono.user/token/datastore/secret/secret.history/access.log
Crypto: crypto.py (PyNaCl SecretBox/Box/SigningKey) + bcrypt (authkey)
Keys:   server identity keypair — odoo.conf params (pillar) or
        /var/lib/odoo/keykeep_psono_keys.conf (auto-generated, mode 600)
```

## Wire format (psono contract)

- All authenticated request bodies and responses are SecretBox-encrypted
  `{text: hex, nonce: hex}` (24-byte nonce, XSalsa20-Poly1305).
- The client adds the `{"data": ...}` wrapper itself — the server must NOT
  double-wrap (breaks clients with UNENCRYPTED_RESPONSE_RECEIVED).
- Login uses Box key exchange; `/info/` is Ed25519-signed (TOFU verify_key).
- Replay protection: `Authorization-Validator` header (encrypted request_time +
  device fingerprint); token deleted on mismatch.

## Deployment (Salt)

`/usr/share/odoo-keykeep/salt/keykeep_psono/init.sls` — installs/upgrades the
module on the ledningssystem minion, optionally pins keys via pillar.

Manual install:

```bash
sudo checkmodule -d ledningssystem -m keykeep_psono
```

## Server identity keys — BACKUP REQUIREMENT

The server identity keypair signs `/info/` (TOFU fingerprint clients approve)
and performs the login Box exchange. The private key lives either in
`/etc/odoo/odoo.conf` (`keykeep_psono_private_key` / `keykeep_psono_public_key`,
managed via Salt pillar) or the auto-generated
`/var/lib/odoo/keykeep_psono_keys.conf` (mode 600).

**Back up the keys together with the database.** Rotating the keys makes all
clients re-approve the server (TOFU) and invalidates the login exchange.

## Client configuration (generated, not static)

`GET /keykeep/psono/web/config.json` is generated by Odoo instead of served
from disk, so operators can change client behaviour without a deploy.

- **Global flags** come from `ir.config_parameter` under `keykeep_psono.*`:
  `allow_registration`, `allow_lost_password`, `allow_delete_account`,
  `allow_custom_server`, `require_email_verification_for_web`.
- **Personal values** (language) come from the signed-in `res.users`, mapped
  to a psono locale (`sv_SE` → `sv`, `pt_BR` → `pt-BR`). Applied only when the
  request carries an Odoo session.
- **Precedence:** global security flags always win. `allow_custom_server` and
  `authentication_methods` never vary between users.
- The response sets `Cache-Control: no-store` (personal values must not be
  cached by a shared cache).
- The shipped `static/src/psono_web/config.json` remains as a fallback for
  clients that cannot reach the dynamic endpoint.

## Vault lifecycle state

`res.users` exposes a derived, non-writable `psono_vault_state`:

```
none ──register──► pending ──verify──► ready ──used──► active
  │                    │                  │              │
ingen rad        rad, ej verifierad   verifierad,    verifierad +
                                       oanvänd        minst en secret/token
```

`psono_registered` and `psono_verified` keep their original meaning
(record exists / email confirmed) and never contradict the state.

**Email verification is per client (design D6).** A client that authenticates
*without* an Odoo session (the browser extension) always requires a verified
email — it is the only identity bridge it has. A session-bound client (the
Odoo-embedded SPA) may skip verification when
`keykeep_psono.require_email_verification_for_web` is `0`. Default is `1`.

## Recovery — the code is never stored (Alt 4)

The recovery code exists **only on the user's side**. The client generates it
locally and sends only:

| Sent to the server | Meaning |
|---|---|
| `recovery_authkey` | `scrypt(recovery_code, ...)` — verifiable, not reversible |
| `recovery_data` | `encrypt({private_key, secret_key}, recovery_code, sauce)` — opaque E2E blob |

The server can verify a submitted code and hand the blob back, but can never
read it — the same principle as `authkey` (bcrypt) and `private_key` (wrapped
by the master password).

**Flow:** `POST /recoverycode/` (register, authenticated) → `POST /password/`
(step 1: verify authkey, return blob) → client decrypts locally → `PUT
/password/` (step 2: install new authkey + re-wrapped keys).

**Consequences you must accept:**

- The server **cannot** recreate or display the code. Support can only report
  whether recovery is registered.
- Losing both the master password and the recovery code means the vault is
  unrecoverable. That is inherent to zero-knowledge, not a bug.
- The Odoo password is **not** the protection of the code. Changing or
  resetting it does not affect the stored recovery material.
- `Min profil → Mitt valv` shows only *whether* recovery is registered and
  when — never the code.

**Not implemented:** mail-based password reset (it would break
zero-knowledge). `POST /password/` and `PUT /password/` are the only reset
path.

## Account deletion

`DELETE /keykeep/psono/user/delete/` requires the vault authkey **and** the
master password, and is refused for sessionless clients. It is **disabled by
default** (`keykeep_psono.allow_delete_account=0`) because it is irreversible:
the vault, tokens, datastores, secrets, history and recovery material are
removed. The linked `res.users` record remains.

Deactivating the Odoo user (`res.users.active = False`) instead *suspends* the
vault (`is_active = False`) without destroying data. Reactivating restores it.

## Translations — known gap

`static/src/psono_web/translations/locale-*.json` are empty (`{}`) except
`locale-en.json`. The language mapping is wired correctly, but a Swedish user
still sees **English strings** until those files are filled. This is a
translation task, not a code change.

## Import / export

Import and export run entirely in the browser (psono-web):
- **Import:** Firefox (CSV), Bitwarden/Vaultwarden (JSON, unencrypted),
  KeePass.info (CSV/XML), KeePassXC, Chrome, 1Password, LastPass, Dashlane,
  Enpass, Proton Pass, Safari, Nextcloud, ... (17+ formats).
- **Export:** JSON, CSV, KeePass (kdbx, password-protected).

Zero-knowledge: import sends only encrypted secrets via `/bulk-secret/`;
export decrypts locally and downloads the file (no server request, not
auditable server-side). Imports are audited in `keykeep.psono.access.log`
(format + count, never content).

## Personal Vault tab (My Profile)

The `res.users` forms have a "Personal Vault" page: registration/verification
status, "Open Vault" (→ psono-web), and deep links to import/export
(`#/other/import`, `#/other/export`). The page is inherited on BOTH the
Settings → Users form (`base.view_users_form`) and the avatar "My Profile"
preferences form (`base.view_users_form_simple_modif`) — the latter is what
regular users see, so without it the tab appears only for admins in Settings.
